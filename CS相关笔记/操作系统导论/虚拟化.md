p[1] 为写入端

```c
// child_first.c
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/types.h>

int main(void) {
    int p[2];
    if (pipe(p) == -1) {
        perror("pipe");
        return 1;
    }

    pid_t pid = fork();
    if (pid < 0) {
        perror("fork");
        return 1;
    }

    if (pid == 0) {
        // 子进程
        close(p[0]);              // 关闭读端
        printf("hello\n");
        fflush(stdout);           // 避免缓冲导致的乱序
        // 向父进程发送一个字节，告诉它可以打印了
        if (write(p[1], "x", 1) != 1) {
            perror("write");
            // 即使出错也尽量退出
        }
        close(p[1]);
        _exit(0);                 // 立即退出子进程
    } else {
        // 父进程
        close(p[1]);              // 关闭写端
        char token;
        // 在这里阻塞，直到子进程写入一个字节
        if (read(p[0], &token, 1) != 1) {
            // 若读失败，仍打印以示意（实际应用可更严格处理）
        }
        close(p[0]);
        printf("goodbye\n");
        fflush(stdout);
        // 不调用 wait() 也可以结束该程序；父进程退出时，僵尸子进程由 init 收割
        // 但在真实程序里，仍建议 wait()/waitpid() 清理子进程避免僵尸。
        return 0;
    }
}
```
# 直接执行

> [!引用]
要执行系统调用，程序必须执行特殊的陷阱（trap）指令。该指令同时跳入内核并将特 权级别提升到内核模式。一旦进入内核，系统就可以执行任何需要的特权操作（如果允许）， 从而为调用进程执行所需的工作。完成后，操作系统调用一个特殊的从陷阱返回 （return-from-trap）指令，如你
期望的那样，该指令返回到发起调用的用户程序中，同时将 特权级别降低，回到用户模式
>
执行陷阱时，硬件需要小心，因为它必须确保存储足够的调用者寄存器，以便在操作 系统发出从陷阱返回指令时能够正确返回。例如，在 x86 上，处理器会将程序计数器、标 志和其他一些寄存器推送到每个进程的内核栈（kernel stack）上。从返回陷阱将从栈弹出这 些值，并恢复执行用户模式程序（有关详细信息，请参阅英特尔系统手册[I11]）。其他硬件 系统使用不同的约定，但基本概念在各个平台上是相似的。

过程调用和系统调用:

过程调用是指**用户程序调用自己或其他用户编写的函数（过程）**。这是编程语言层面的调用，如在 C 语言中调用 `printf()`、在 Python 中调用 `len()`。

系统调用是**操作系统提供给应用程序访问内核功能的一种接口**。当用户程序需要执行某些**只能由操作系统完成的操作**（如文件读写、进程控制、网络通信等）时，必须通过系统调用.
- 由用户态切换到内核态执行
- 由操作系统提供,通常通过中断或者陷阱指令(trap)(如 int 0x80, syscall)实现
- 能访问硬件资源(CPU, 磁盘, 内存等)
- 执行开销比较大,因为设计上下文切换

## 受限直接运行协议

**RDE** 的核心思路是：
> 让用户程序在 CPU 上直接运行（获得高性能），但只允许它执行“非特权指令”；  
> 当它想做“敏感操作”（如系统调用、I/O、内存访问）时，必须通过 **陷入（trap）** 操作，交回控制权给操作系统。

工作流程:
1. **启动程序阶段**
    - 操作系统创建一个进程，为它分配内存空间、加载程序代码和数据。
    - 然后操作系统设置好CPU的**模式位（mode bit）**，从“内核态”切换到“用户态”。
    - 最后通过一条“跳转到用户程序入口”的指令，让程序开始执行。
2. **运行阶段**
    - 在用户态下，程序只能执行普通（非特权）指令，比如算术运算、逻辑判断、用户空间的内存读写。
    - 如果程序执行敏感操作（如系统调用），需要通过 `trap` 指令触发陷入内核：
        - CPU切换到**内核态**；
        - 执行操作系统内核中对应的**系统调用服务例程**；
        - 执行完毕后通过 `return-from-trap` 返回用户态继续运行。
3. **中断与调度**
    - 为防止程序长期占用CPU，操作系统设置了**定时器中断（timer interrupt）**。
    - 当时间到时，中断会让CPU自动陷入内核，操作系统可以保存当前进程状态并切换到其他进程，实现多任务。
	
### 陷阱表
非常好，这个问题和“受限直接运行协议”关系非常密切。下面我来系统地解释一下——
#### 一、陷阱表（Trap Table）的定义
**陷阱表（Trap Table）** 是操作系统在 **内核空间中维护的一张“中断/异常处理入口表”**，  
用于告诉 CPU：
> 当某种“陷阱（trap）”发生时，应该跳转到内存的哪个地址去执行对应的处理程序。
> 换句话说，它是**CPU在陷入内核时的导航图**，让处理器知道“该去哪执行内核代码”。

#### 二、什么是“陷阱”（Trap）
“陷阱”（trap）是 CPU 从用户态进入内核态的机制之一，用于处理三类事件：

| 类型                    | 举例                              | 是否由程序主动触发 |
| --------------------- | ------------------------------- | --------- |
| **系统调用（System Call）** | 如 `read()`, `write()`, `open()` | ✅ 是       |
| **异常（Exception）**     | 除以零、非法内存访问、缺页中断                 | ❌ 否       |
| **中断（Interrupt）**     | 外部设备事件（如时钟、键盘输入）                | ❌ 否       |
#### 三、陷阱表的作用
当系统发生陷阱时，CPU必须：
1. **切换到内核态**；
2. **保存当前用户程序的状态（寄存器、PC等）**；
3. **找到对应的内核处理函数（Handler）入口地址**；
4. **跳转执行该函数**。

而“找到对应的入口地址”这一步，就是靠 **陷阱表（Trap Table）** 完成的。
陷阱表中存储了每一种陷阱的处理程序地址（函数指针或偏移量）。

#### 四、工作原理（简化示意）
1. **操作系统在启动（开机）时建立陷阱表**：
    ```c
    trap_table[0] = handle_divide_by_zero;
    trap_table[1] = handle_page_fault;
    trap_table[2] = handle_syscall;
    trap_table[3] = handle_timer_interrupt;
    ...
    ```
2. 将陷阱表的基地址告诉CPU（通过特殊寄存器，例如 x86 的 **IDTR（Interrupt Descriptor Table Register）**）。
3. 当陷阱发生时：
    - CPU 根据陷阱号（trap number）在陷阱表中查找对应入口；
    - 自动切换到内核态；
    - 跳转到处理函数；
    - 处理完毕后通过 `return-from-trap` 返回用户态继续执行。
#### 五、陷阱表与RDE的关系
在 **受限直接运行协议（RDE）** 中，陷阱表是实现“受限”的关键机制之一。  
用户程序无法直接操作硬件，但可以通过“陷入”访问操作系统提供的服务。

> 当用户程序执行 `trap` 指令（或系统调用）时，  
> CPU 查陷阱表 → 进入对应系统调用处理程序 → 执行内核代码。

因此，陷阱表是 RDE 协议的**桥梁**，连接“用户态程序”与“内核态服务”。

#### 六、陷阱表 vs 中断向量表（区别与联系）

| 项目       | 陷阱表（Trap Table）                      | 中断向量表（Interrupt Vector Table） |
| -------- | ------------------------------------ | ----------------------------- |
| 作用范围     | 包含异常、系统调用、外部中断                       | 通常只包括外部中断                     |
| 内容       | 各类陷阱的入口地址                            | 各类中断的入口地址                     |
| 是否包含系统调用 | ✅ 是                                  | ❌ 否                           |
| 常见平台术语   | x86: IDT（Interrupt Descriptor Table） | x86中IDT兼作两者                   |
实际上，在现代操作系统（如Linux）中，这两者往往被合并成一张统一的“中断描述符表”（IDT）。

## 课后作业
通过内联汇编调用tatsc指令计算指令调用大概需要的时间

```c
#include <stdio.h>
#include <stdint.h>

static inline uint64_t rdtsc(void) {
    unsigned int lo, hi;
    __asm__ __volatile__ ("rdtsc" : "=a"(lo), "=d"(hi));
    return ((uint64_t)hi << 32) | lo;
}

int main() {
    double cpu_ghz = 2.419;  // 你的CPU频率 (GHz)
    uint64_t start = rdtsc();

    for (volatile int i = 0; i < 100000; i++); // 测试区间

    uint64_t end = rdtsc();
    uint64_t cycles = end - start;

    double ns = cycles / cpu_ghz;  // 每个GHz = 1e9 cycles/s → 1cycle = 1/ns
    printf("Cycles: %llu\n", (unsigned long long)cycles);
    printf("Elapsed: %.2f ns (%.3f µs)\n", ns, ns / 1000.0);
    return 0;
}

```

# 进程调度
## 度量指标

**周转时间**
$$ T_{周转周期} = T_{完成时间} - T_{到达时间} $$
减少周转时间的策略
- 最短完成时间优先


**响应时间**
$$ T_{响应时间} = T_{首次运行} - T_{到达时间} $$
减少相应时间的策略
- 轮转机制
	通常来说时间片越短,对于响应时间提升越好.但是突然的上下文切换会影响操作系统的性能

> [!提示: 摊销技术]
>当系统某些操作有固定成本时，通常会使用摊销技术（amortization）。通过减少成本的频度（即执行较少次的操作），系统的总成本就会降低。例如，如果时间片设置为10ms，并且上下文切换时间为1ms， 那么浪费大约10%的时间用于上下文切换。如果要摊销这个成本，可以把时间片增加到100ms。在这种情况下，不到1%的时间用于上下文切换，因此时间片带来的成本就被摊销了

第一种类型（SJF、STCF）优化周转时间，但对响应时间不 利。第二种类型（RR）优化响应时间，但对周转时间不利。我们还有两个假设需要放宽： 假设4（作业没有I/O）和假设5（每个作业的运行时间是已知的）。接下来我们来解决这些假设。
